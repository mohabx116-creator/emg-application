# EMG Technical Architecture v0.1

## 1. الهدف

بناء نظام سريع وآمن وقابل للتوسع، مع فصل الواجهة عن الـBackend، والحفاظ على إمكانية إضافة تطبيق موبايل مستقبلًا.

## 2. المستودعات

### Frontend repository

- React.
- TypeScript.
- Berry Material React.
- MUI وRTL وCairo.
- صفحات مخصصة للمشاريع والحركات والموردين والتقارير.
- استهلاك REST API أو API متفق عليه من الـBackend.

النسخة الحالية الموجودة في المشروع تستخدم React وTypeScript وVite. يوجد ملف Berry آخر باسم Next، لكن اختيار Next.js أو Vite يتم بعد مراجعة النسخة التي سيتم اعتمادها فعليًا، ولا يتم خلط البنيتين داخل نفس التطبيق.

### Backend repository

- .NET Web API.
- طبقات منفصلة للـAPI والمنطق وقواعد البيانات.
- Authentication وAuthorization.
- Validation.
- Approval workflow.
- Audit log.
- تصدير Excel وPDF.

### Database

- PostgreSQL.
- معاملات مالية دقيقة باستخدام numeric وليس floating point.
- Foreign keys وقيود لمنع الحركات غير المرتبطة.
- فهارس على المشروع والمورد والتاريخ والحالة.
- Migrations قابلة للتتبع.

## 3. فصل المسؤوليات

```text
Frontend
  ↓
Backend API
  ↓
Business Rules
  ↓
PostgreSQL
  ↓
File Storage
```

الواجهة لا تحسب الحسابات النهائية ولا تفرض الصلاحيات وحدها. الـBackend هو مصدر تنفيذ القواعد.

## 4. Authentication وAuthorization

- حساب لكل مستخدم.
- أدوار متعددة للمستخدم الواحد.
- صلاحيات على مستوى الشركة والمشروع والقسم ونوع الحركة والإجراء.
- تكليف مهندس بالمشروع له تاريخ بداية ونهاية.
- منع رؤية المشاريع غير المسموح بها من الـBackend.
- سجل لمحاولات الوصول المرفوضة.
- دعم إيقاف الحساب وإعادة تعيين كلمة المرور.

## 4.1 ملف المستخدم واسترداد كلمة المرور

- Username ثابت لا يتغير بعد إنشاء الحساب.
- Display name قابل للتعديل.
- Avatar أو صورة شخصية.
- تغيير كلمة المرور من داخل الحساب.
- Password reset عبر رمز أو رابط مؤقت منتهي الصلاحية.
- إبطال الجلسات القديمة عند تغيير كلمة المرور عند الحاجة.
- عدم تخزين كلمات المرور نصًا صريحًا.
- مسؤول المنظومة يستطيع عمل Reset من لوحة الإدارة.
- كلمة الـReset تكون افتراضية أو مؤقتة، ويجبر المستخدم على تغييرها بعد الدخول.

## 4.2 البحث الشامل

يوفر الـBackend Search API موحدًا مع احترام نطاق صلاحيات المستخدم. يدعم البحث في المشاريع والأطراف والحركات والفواتير والتحويلات والمرفقات والملاحظات، مع pagination وfilters وsorting.

يتم استخدام فهارس مناسبة في PostgreSQL، مع إمكانية إضافة full-text search عند زيادة حجم البيانات.

## 4.3 التنبيهات والإشعارات

- Notification entity مرتبطة بالمستخدم والمشروع والحركة عند الحاجة.
- حالة مقروء وغير مقروء.
- نوع الإشعار وأولويته.
- رابط مباشر إلى الشاشة أو الحركة.
- تفضيلات لكل مستخدم.
- In-app notifications في البداية.
- قابلية إضافة البريد أو Push Notifications لاحقًا.

الإشعارات الناتجة عن الاعتماد أو المستندات الناقصة أو الدفعات غير الموزعة ينشئها الـBackend بعد نجاح العملية، وليس من الواجهة فقط.

## 5. المعاملات المالية

كل عملية مالية تعتمد على معاملات قاعدة بيانات Transaction لضمان عدم حفظ جزء من الحركة دون الجزء المرتبط به.

مثال عند اعتماد دفعة:

```text
حفظ الدفعة
+ حفظ التوزيعات
+ تحديث حالة المستحق
+ تسجيل سجل التدقيق
```

إما أن تنجح العملية كلها أو تفشل كلها.

## 6. المستندات والملفات

الملفات لا تخزن داخل جداول PostgreSQL كبيانات ضخمة. يتم تخزينها في File Storage، بينما تحفظ قاعدة البيانات:

- اسم الملف.
- نوعه.
- حجمه.
- مكانه.
- المشروع.
- الحركة المرتبطة.
- المستخدم.
- تاريخ الرفع.
- إصدار التصميم عند الحاجة.

## 7. الأداء

- Pagination في الجداول.
- بحث وفلاتر من قاعدة البيانات.
- عدم تحميل كل حركات المشروع مرة واحدة.
- Lazy loading للأقسام الثقيلة.
- تقارير مجمعة عبر استعلامات محسنة.
- فهارس على الحركات والتواريخ والأطراف.
- Cache محدود للبيانات الثابتة مثل الوحدات والأقسام.
- Background jobs للتصدير الكبير أو معالجة الملفات.
- بحث شامل باستخدام فهارس وفلاتر من قاعدة البيانات.
- تحميل الإشعارات بشكل تدريجي وعدم تحميل السجل كاملًا دفعة واحدة.

## 8. قابلية الموبايل

الـBackend لا يعتمد على شكل الويب. كل عمليات المهندس تكون عبر API قابلة للاستخدام من:

- Web.
- PWA مستقبلًا.
- تطبيق React Native أو غيره.

شاشات المهندس تصمم Mobile-first في العمليات اليومية مثل تسجيل حركة أو رفع صورة، مع الاحتفاظ بشاشات الإدارة والجداول الكبيرة للويب.

## 9. الاستضافة

البداية يمكن أن تكون على VPS واحد منظم، مع فصل الخدمات منطقيًا:

- Frontend deployment.
- Backend service.
- PostgreSQL.
- File storage أو volume منفصل.
- Reverse proxy وTLS.
- Backups.
- Monitoring وlogs.

مع إمكانية فصل قاعدة البيانات والتخزين والـBackend لاحقًا دون إعادة بناء النظام.

## 10. قرار الـFrontend

تم اعتماد نسخة React + Vite الموجودة حاليًا كأساس للـFrontend. لا يتم خلطها مع نسخة Berry Next.js داخل نفس التطبيق.
