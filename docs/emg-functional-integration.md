# EMG functional integration

## Workbook upload and preview

Use multipart `POST /api/universal-import/preview` with field `file`. This requires `data.migrate`. The API accepts an original XLSX and returns a read-only preview.

- `sourceProjectCode` is the plot identifier found in the source. `projectMetadata` adds nullable `clientName`, `ownerName`, `payerName` and `location`. Display empty fields for missing evidence and allow the user to enter project metadata explicitly.
- `issues[]` contains `code`, `sheetName`, `sourceCoordinate`, nullable `recordId` and an Arabic `message`. Section issues use a range. Record issues use the source coordinate and stable preview record ID. The first codes are `SHEET_MAPPING_REQUIRED`, `ROW_MAPPING_REQUIRED` and `ROW_UNRESOLVED`.
- Show `sections`, `records`, `reconciliations` and `duplicateCandidates` alongside the issues. Summary and derived records retain their original types. Financial streams and currencies remain separate. `eligibleForPosting` describes source classification and does not grant mutation authority.
- A malformed upload returns HTTP 400. Retain any existing user inputs while displaying the server message.

The new-project flow uses the `snapshotId` from universal preview. Send it with the project metadata and optional `mappingEvidence` keyed by preview record ID to `POST /api/universal-import/revalidate`. The response lists the target, source coordinate, amount and eligibility or exclusion reason for each record. Only evidence-backed mapping confirmations are editable. Source amounts, relationships and currency come from the server snapshot.

Send the same request to `POST /api/universal-import/commit` with explicit `confirmExcluded` when the user has reviewed the unresolved records. Commit revalidates the snapshot and writes the project, operational rows, retained records, audit and provenance in one serializable transaction. It returns `projectId`, `batchId`, counts and totals by operational target. Duplicate sources and project codes yield a conflict. Reports read the operational rows as soon as commit succeeds.

Commit requires an administrator and uses the `UniversalImportQa` settings to allow only one approved workbook SHA-256 in a named disposable loopback PostgreSQL database on a non-5432 port. Posting stays disabled in Production. The project-scoped historical review under `/api/universal-import/review` remains the route for existing projects and settlements. The new-project screen uses only the universal endpoints.

## Accounting

Final Accounts and the consolidated statement use a shared calculation for the office fee and outstanding fee. In the consolidated response, use `officeAccrual.officeFee` and `officeAccrual.officeOutstanding` when `isOfficial` is true. The base includes each recognized operational source row once. Owner funding, funding allocations, supplier liabilities and supplier payments are separate dimensions. With unresolved operational classification, the official values are null and only the diagnostic amount is available. The net-transaction calculation remains subject to source reconciliation.

For supplier-linked invoices, the source link must identify the original site transaction. Supplier liabilities and payments are account dimensions. Adding either dimension to operating costs would count the same purchase twice. The canonical invoice API is `POST /api/suppliers/invoices`, `GET /api/suppliers/invoices/{id}`, `PUT /api/suppliers/invoices/{id}` and `DELETE /api/suppliers/invoices/{id}` with `suppliers.supplies-create`/`suppliers.view`, creator ownership, explicit correction/cancellation grants and project scope. It stores one `SupplierInvoice` header, multiple `SupplierInvoiceLine` records, and exactly one `SupplierSupply` ledger line per invoice line; when no source movement is supplied, the backend creates the linked direct-posted site movement in the same serializable transaction. The returned `id`, `invoiceNumber` and `siteMovementId` are the canonical source links. Initial payment is bounded by the backend-computed EGP total, and the returned `paidAmount`/`outstandingAmount` support cash (39,223/39,223/0), credit (39,223/0/39,223) and partial (39,223/20,000/19,223). Existing linked payments re-check remaining payable inside a serializable transaction. Zero or multiple attachments use the existing attachment API with entity type `supplier-invoice`; deleting an unpaid invoice removes its verified attachment metadata and files after the aggregate commit. Inline supplier creation remains available through `POST /api/suppliers/inline-supply`. Editing preserves line count and refuses to lower an invoice below posted payments; paid invoices are protected until their dependent payments are handled. The site-movement and supplier-liability dimensions remain separate so the same purchase is not counted twice.
Non-supplier multi-line site entries use `POST /api/site-movements/batch`, which validates one project and commits all lines plus their direct-posting workflow actions in one serializable transaction. A site movement linked to `SupplierInvoice` is read-only through the generic site-movement update/delete endpoints; deletion must use the invoice aggregate so dependent payments and attachments cannot be bypassed. The site movement response exposes `invoiceId` for this routing decision.
